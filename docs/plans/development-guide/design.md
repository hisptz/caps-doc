# Development guide — design

The Development Guide is the contributor path on the CAPS docs site: run both repositories on a laptop, find the code that owns a change, and open a pull request. The tab already exists (`Development Guide` → `/development-guide/`). The landing page is a stub.

## Who it is for

Someone who will change caps-engine, caps-app, or both. They can use a terminal, Git, and Docker. They may be new to DHIS2 apps or to the pipeline worker. They are not installing CAPS for a ministry (Deployment Guide) and they are not operating pipelines day to day (User Guide).

Write to that person in the second person. Point at files and commands. Do not restate a whole module when a path and a one-line role will do.

## What “ready to change CAPS” means

A reader is done with the setup pages when:

1. Postgres and RabbitMQ are up, and the engine API, worker, and scheduler reload on the host with `bun run dev:*`.
2. The DHIS2 app runs at `http://localhost:3000` and can reach an engine through a Route with code `caps`.
3. They know which repository owns the change they have in mind.
4. They can run the same checks CI runs for that repository.

The guide stops at a merged-quality pull request. Production image pins, backups, and the operator handover stay in the Deployment Guide.

## Three guides, three jobs

| Guide | Question it answers | Keep out of the development guide |
| --- | --- | --- |
| User Guide | How do I run and watch pipelines? | Field-by-field operator manual |
| Deployment Guide | How do I install and connect CAPS for use? | `make up` as the production path, backup, TLS, scaling |
| Development Guide | How do I change CAPS? | Ministry install checklists |

`make up` appears here only as the way to get Postgres, RabbitMQ, and a migrated database on a laptop. Say that the same Makefile target compiles distroless images, and that daily work uses the host `dev:*` scripts against the published ports. Link to the Deployment Guide for anything an operator would do with those images.

## How a page should read

Each page has the same spine:

1. **Before you start** — the other page or tool that must already be in place.
2. **Steps** — commands and the file to open. One repository per section when the tools differ.
3. **Check** — the process, URL, or test result that means it worked.
4. **Where this lives** — a short map of directories for the next edit, not a tour of every file.

Use admonitions for rules that break a pull request:

- caps-engine is Bun. Do not document npm, pnpm, or Node for that repo.
- caps-app is pnpm and the DHIS2 App Platform. Do not document Bun or `yarn start` for that repo.
- The app uses `HashRouter`. URLs look like `http://localhost:3000/#/pipelines`.
- Browser calls go through `src/capsApi` and the DHIS2 Route `routes/caps/run`. Do not add a direct `fetch` to the engine origin.
- User-facing strings go through `i18n.t()`.
- Exactly one scheduler process. A host `dev:scheduler` plus the Compose scheduler will double-fire pipelines.
- Hot reload does not exist inside the distroless images. `docker exec` will fail on api, worker, and scheduler.

Prefer a directory tree and a link to the source file over a screenshot of an editor. Prefer a screenshot only when the reader must recognize a DHIS2 screen (the local app shell, the welcome route form).

## Two repositories, one product

Open with this split and repeat it wherever a task could land in the wrong repo.

| Change | Repository | Tooling |
| --- | --- | --- |
| HTTP API, worker, scheduler, Prisma, handlers, queues | [hisptz/caps-engine](https://github.com/hisptz/caps-engine) | Bun, Vitest, Docker Compose |
| DHIS2 screens, Route setup, forms that edit handler config | [hisptz/caps-app](https://github.com/hisptz/caps-app) | pnpm, DHIS2 App Platform, Jest, Playwright |
| This documentation site | [hisptz/caps-doc](https://github.com/hisptz/caps-doc) | pnpm, Astro Starlight |

A new pipeline step usually touches both products: a handler and Zod schema in the engine, and a form in the app whose key matches the `Handlers` enum string. The handler page is where that contract is taught. Do not split it into “backend only” and leave the form as a surprise.

## Voice

- Name the command that CI runs, not a prettier alias.
- When a README and a script disagree, follow the script and mark the README in the materials plan as **confirm**. Several app docs still describe an older `pnpm start` and an older CI workflow.
- Demo passwords (`admin` / `district`, `caps` / `caps`) are for the local stack only. Say so once on the engine setup page.
- Do not paste tokens or a private DHIS2 URL.

## Shape in the site

Published pages live in `src/content/docs/development-guide/`. The sidebar is autogenerated (`src/tabs.ts`). The index stays `sidebar.order: 0` with label “Start developing”.

```yaml
---
title: Run the engine locally
description: Start Postgres and RabbitMQ, then reload the API on the host.
sidebar:
  label: Engine
  order: 2
---
```

Internal links omit the site base (`/development-guide/engine/`). The site `base` is `/caps-doc`.

## What the landing page should do

Replace the stub note on `development-guide/index.md` with:

- Who the guide is for.
- The two application repositories and the docs site.
- The path through the sidebar: local engine, local app, code map, a handler change, tests, a pull request.
- A pointer to the Deployment Guide for anyone who arrived here wanting a server install.

No install novel on the landing page. The first command belongs on the engine page.
